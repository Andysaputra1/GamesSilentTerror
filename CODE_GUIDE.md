# Code guide

This file is for anyone reading or changing the code. It covers folder structure, layer boundaries, main flows,
bot brain locations, coding style, and running tests and simulations. Game rules and bot behavior are in
[GAME_CONCEPT.md](GAME_CONCEPT.md); application setup is in [README.md](README.md).

## Core principles

- **The backend is the source of truth.** Permissions, phases, roles, and victory are determined by the engine
  in `backend/app/game/match_engine.py`. The frontend only displays snapshots and sends user requests.
- **A bot is a player without a browser.** Bots use the same service as players (`services/room_service.py`)
  and do not modify `Match` directly.
- **Matches live in one process's memory.** MySQL stores accounts, chat archives, traces, and surveys, not
  match state. See [Implementation limits](#implementation-limits).

Common terms:

| Term | Meaning |
| --- | --- |
| `Match` | The engine object for one match: roster, roles, phase, actions, votes, winner |
| Snapshot | Match data generated by the engine for **one** player (`Match.snapshot(nama)`); other players' private information is excluded |
| Phase token | The `match_id`, `round_number`, and `phase` tuple sent with an action. Stale-token actions are rejected |
| Memory (Ingatan) | One bot's match records (`bot/ingatan.py`): observed chat, votes, and facts |
| Trace (Jejak) | Stages and durations for one human message or bot step, displayed in the Checker panel |
| Fingerprint (Sidik) | A SHA-256 hash of bot decisions with fixed seeds (`tests/jejak/sidik.json`), used to verify unchanged logic |

## Layer rules

| Layer | Responsibility | Restrictions |
| --- | --- | --- |
| `controllers/` | Validate requests through `schemas/`, authenticate routes, call services, translate errors to HTTP | No database transactions or SQL |
| `middleware/` | Bearer tokens, login attempt limits, CORS, 422 responses | No game rules |
| `sockets/` | Socket.IO events. Sockets serve public chat only; actions and snapshots use HTTP | Does not determine chat permissions itself; calls `chat_service` |
| `services/` | Application rules, locks, and transaction boundaries (`jalankan_transaksi`) | Does not import `fastapi`, since controllers and bots both use services |
| `models/` | Direct SQL with `sqlalchemy.text` and bound parameters | No HTTP rules or API response construction |
| `game/` | Pure match rules | No dependency on HTTP, Socket.IO, MySQL, or LLMs |
| `bot/` | Thinking: read snapshots, decide, generate dialogue | No SQL; acts through `services/room_service.py` |

`tests/test_structure.py` checks three structural rules: SQL `text` appears only in `models/` (except the
`SELECT 1` connection check in `config/database.py`), controllers do not open transactions, and services do not
import `fastapi`.

Call direction:

```text
HTTP       -> controllers -> services -> game (Match) / models (SQL) -> MySQL
Socket.IO  -> sockets/chat.py -> services/chat_service.py -> models -> MySQL -> emit_room
0.5-second clock (main.py) -> room_service.perbarui_fase_semua_room        (advance expired phases)
                          -> npc_service.jalankan_bot_yang_sudah_waktunya (step bots that are due)
                          -> every 60 s: room_service.bersihkan_room_diam (abandoned lobbies/completed rooms)
                          MySQL unavailable: room_service.jeda_jam_semua_room (pause phases and bots)
```

MySQL queries initiated by the event loop (socket-token checks, player chat storage, `/app-status`) run in
threads, and every connection has timeouts. Details, including queries that still hold the room lock, are in
[backend/README.md](backend/README.md#when-mysql-has-problems).

Model SQL examples and service usage are in [backend/README.md](backend/README.md#sql-patterns-in-models).

## Main flows

1. **Login and registration.** The `Auth` component calls `controllers/auth.py`; `auth_service` validates identity
   and stores the session-token hash. After success, `BootLoader.bukaSesudahLogin` opens Main behind a loading
   screen until rendering finishes. See [Accounts, sessions, and login](#accounts-sessions-and-login).
2. **Session recovery.** Guards and `ActiveMatchService` ask the server for an active match
   (`GET /api/rooms/active`). Accounts still playing return to `/game` from any tab. Roles and permissions always
   come from the backend snapshot, not browser storage.
3. **Lobby.** `Lobby` → frontend `RoomService` → `controllers/rooms.py` → `room_service`. Room membership lives
   in backend process memory. Every member call (`room_service.get`, `join`) records the room's last access;
   the game clock removes lobbies idle for one hour and completed rooms idle for 30 minutes, after their
   participants are archived for surveys. Failed `POST /api/rooms/join` attempts are limited to 10 per account
   and 30 per IP per minute. Lobby polls `GET /api/rooms/{code}` every 3 seconds while its tab is visible.
4. **Start.** The host calls `POST /api/rooms/{code}/start`. A `Match` is created with random roles and remains
   in `preparing` until the bot brain is ready or the wait limit expires.
5. **Player actions.** `GameService` sends an action to `POST /api/rooms/{code}/play` with a phase token.
   `room_service` advances the phase, checks the token, then calls `Match.act` or `Match.vote`. The engine checks
   role, target, phase, and cooldown. The browser polls `GET /api/rooms/{code}/game` every second; `snapshot(viewer)`
   restricts information to the viewing player. Polling stops while the tab is hidden (one fetch when visible
   again) and after a winner exists. The results screen and survey use the final snapshot, and abandoned completed
   rooms are no longer touched, allowing cleanup. After a winner exists, a server 400 (for example, another tab
   created a new room) does not eject the player from the survey screen.
6. **Nighttime team chat.** `POST /api/rooms/{code}/team-chat`. Messages live only in `Match` memory and
   `me.team_messages`, deliberately without sockets, database storage, NLU, or `@traced`.
7. **Human public chat.** `sockets/chat.py` (`send_chat`) → `chat_service.kirim_chat_pemain`: validate message and
   session → check chat permission (`can_chat`) → per-player, per-room rate limit (2-second gap, 5 messages per
   20 seconds) → store in MySQL → send `receive_chat` to the room → IndoBERT reads through `catat_nlu`.
   Rejections return to the sender as `system_alert`; the game page restores rejected text to the input box.
   Socket.IO does not reconnect sockets rejected during handshake (invalid token/room or a temporary MySQL
   failure), so the game page retries with the latest token after 2, 4, 8 … seconds, capped at 30.
   `tryAllTransports` uses HTTP long-polling if the network blocks WebSocket. Before broadcasting, `emit_room`
   removes sockets that left the room or whose sessions were revoked, and skips sockets whose tokens cannot yet
   be checked because MySQL failed. Broadcasts within one room are sent in order.
8. **Bot steps.** See [One bot step](#one-bot-step).
9. **Panel.** Administrator sessions are separate from player sessions. Checker displays explanations for each
   bot step, generated by `bot/penjelasan.py` in `BrainRuntime.langkah` and supplemented with engine/NLG results
   by `isi_jejak` (`bot/bot_controller.py`). The trace list carries only `ringkas`; full explanations are fetched
   per trace through `GET /api/panel/checker/{code}/jejak/{id}`. Both endpoints are async: ongoing traces are
   copied in the event loop where chat and bot steps modify them, while archives are read in a thread. Ongoing
   work is fetched every second through `GET /api/panel/checker/{code}/proses` (`panel_service.proses_checker`):
   unfinished trace stages and durations (`checker_service.proses_berjalan`), live bot state
   (`NPCService.kondisi_bot`), and brain/writer queues recorded by `EksekutorTercatat` in
   `services/checker_service.py`. API key values are never sent back to the browser.
10. **Logout and sessions.** `ProfileMenu` → `SessionService` → `POST /api/auth/logout`. After token revocation or
    expiry, browser session data is cleared and the user is sent to login. If the server is unreachable, the
    local session is still removed and login shows a warning; the server token expires on its own. Logout does
    not stop the match. A 401 for a stored token is handled by one interceptor (`sesiDitolakInterceptor` in
    `core/session.service.ts`): clear the local session and open login with "Sesi berakhir" (Session expired).
    Logging into another account in another tab replaces the token used by all tabs, so this tab forgets its
    room and reloads Main with "Akun berganti di tab lain" (Account changed in another tab), handled by `App`.
    One browser = one account; test two accounts using an incognito window or another browser profile.

## Bot brain in code

All bot logic is in `backend/app/bot/`. This code is the source of game logic; thesis notebooks are only reports.

| File | Contents |
| --- | --- |
| `bot_controller.py` | `NPCService` (scheduling, one bot step's sequence, speaking floor) and `BrainRuntime` (shared brain: loads NLU, fuzzy logic, and writers; each bot's memory and persona) |
| `nlu.py` | IndoBERT chat interpretation: intent, then target; name rules for neutral messages; per-match memo shared by all bots and the NLU recorder |
| `ingatan.py` | Inputs: one bot's `Ingatan`, then chat, votes, and facts converted to 0–1 evidence per player (`hitung_bukti`, `pengetahuan_peran`, `fitur_hitman`, `fitur_lindung`). No fuzzy logic here |
| `fuzzy_controller.py` | Main controller: `putuskan` and all logic surrounding fuzzy calls, in order [FUZZY 1] → Tribunal → Discussion → Night → package decisions |
| `fuzzy/` | Fuzzy functions only: one system = one function. `mesin.py` contains curves, the Mamdani system builder, cache, and `SEMUA_SISTEM` |
| `nlg_controller.py` | Main NLG controller: `tulis_pesan` (public chat) and `tulis_chat_tim` (team chat) sequence [PROMPT] → [PENULIS LLM] (LLM writer) → [PERIKSA ATURAN] (rule checking), with at most 2 LLM attempts, then [TEMPLAT] (templates) and fallback |
| `nlg/` | Dialogue writer implementation, one file per stage: `prompt.py` [PROMPT] LLM instructions; `penulis.py` [PENULIS LLM] OpenRouter/custom endpoint chain; `aturan.py` [PERIKSA ATURAN] rule checker; `templat.py` [TEMPLAT] personas and template variants; `pengaturan.py` [PANEL] panel-configured writer chain (`PenulisNPC`) |
| `penjelasan.py` | Bot decision explanations for the Checker panel |
| `simulasi.py` | Panel menu 07 simulation using the same engine, brain, NLU, and NLG, with dedicated simulation threads |

Import direction: `fuzzy_controller` imports `ingatan` and `fuzzy/`; `ingatan` imports no other bot files; files
in `fuzzy/` import only `fuzzy/mesin.py`. NLG follows the same pattern: `nlg_controller` imports stages from
`nlg/` and calls them by module name (`prompt.buat_prompt`, `aturan.periksa_aturan`, `templat.kalimat_templat`).
Cross-stage imports are limited to `prompt` → `aturan` and `templat`, `penulis` → `aturan`, and `pengaturan` →
`penulis`. `BrainRuntime._muat` loads brain modules at server startup. The NLG structure is explained in the
Bedah Otak Fuzzy (Fuzzy Brain Walkthrough) web document, NLG section, *Susunan kode NLG* (NLG Code Structure).

### One bot step

The clock in `main.py` calls `NPCService.jalankan_bot_yang_sudah_waktunya` every 0.5 seconds. For each due bot:

1. `room_service.lihat_untuk_bot`: the bot's private snapshot (only brain-used fields) and observed phase token.
   Hostage victims are not scheduled.
2. `BrainRuntime.langkah`: `Ingatan.sinkron_snapshot` records the snapshot → `nlu.baca_chat_baru` reads new chat
   with IndoBERT → `fuzzy_controller.putuskan`.
3. `room_service.pilihan_bot`: apply a vote or secret action only if the observed phase has not changed.
   A phase is marked as brain-owned (`npc_decisions`) only when the vote/action is accepted or the brain
   intentionally does nothing; "wait" does not mark it. A decision reaching the engine without rejection also
   consumes that night's lock-in opportunity.
4. Team chat if a human teammate exists (`room_service.chat_tim_bot`), without a speaking floor, database,
   broadcast, or NLU.
5. Public chat: `NPCService._ambil_giliran_bicara` (per-phase speaking floor, at most `LANTAI_MAKS` = 3 bots
   composing concurrently without duplicate plans) → rule-checked dialogue from `nlg_controller.tulis_pesan`
   (templates only if < 20 seconds remain) → `room_service.chat_bot` (store) → IndoBERT reads it in the background.
6. Panel trace (`isi_jejak`), then `emit_room("receive_chat")`.

### The `putuskan` sequence

`putuskan(ingatan, view)` is the only decision function called by the game and simulation. The module docstring
in `fuzzy_controller.py` lists its steps in order; briefly:

1. **[FUZZY 1] Evaluate players.** Town: `hitung_bukti` → suspicion tree (7 systems) → confirmed facts override
   scores (`terapkan_pengetahuan`). Hitman: public evidence → suspicion → `fitur_hitman` → threats and scapegoats
   (4 systems).
2. **Tribunal.** Switch votes during extra time, guaranteed vote (Peek result), then `keputusan_vote` (town:
   `keyakinan_vote` → `kesiapan_vote` → threshold → forced vote) or `keputusan_vote_hitman`.
3. **Discussion.** `chat_pasti` when a Peek result must be revealed; otherwise `keputusan_chat`: chat candidates
   → `fuzzy/diskusi.py` systems → sort → `AMBANG_CHAT`.
4. **Night actions.** `keputusan_aksi`: Hostage, Gag, Guard, or Peek candidates → `fuzzy/malam.py` systems
   (Gag, Peek) → select.
5. **Package.** `format_npc` (engine), `siapkan_nlg` (dialogue writer), `siapkan_nlg_tim` (team chat).

Within each session, logic shared by all roles comes first, followed by role-specific logic.

### Fuzzy system list

Every system uses two 0–1 inputs, three levels (`rendah`, `sedang`, `tinggi`: low, medium, high), 9 rules, and a
0–100 centroid output. Curves are `MF_INPUT` and `MF_OUTPUT` in `fuzzy/mesin.py`. Import order in
`fuzzy/__init__.py` determines `SEMUA_SISTEM` order.

| File | Stage | Systems |
| --- | --- | --- |
| `fuzzy/kecurigaan.py` | [FUZZY 1], town | `sentimen_sosial`, `perilaku_mencurigakan`, `jejak`, `kejanggalan`, `ucapan`, `bukti_keras`, `kecurigaan` |
| `fuzzy/ancaman.py` | [FUZZY 1], Hitman | `ancaman_langsung`, `ancaman_peran`, `ancaman`, `kambing` |
| `fuzzy/diskusi.py` | [FUZZY 2], chat | `tuduh`, `bela_orang`, `ajak_bicara`, `tanya_info`, `h_tuduh`, `klaim_palsu` |
| `fuzzy/tribunal.py` | [FUZZY 2], town votes | `keyakinan_vote`, `kesiapan_vote` |
| `fuzzy/malam.py` | [FUZZY 2], night actions | `gag`, `intip` |

There are 21 systems in total. Chains (for example, `sentimen_sosial` and `perilaku_mencurigakan` → `ucapan` →
`kecurigaan`) are written as ordinary calls in `fuzzy_controller.py`.

### Changing bot logic

1. Edit code directly in `backend/app/bot/`.
2. Run scenarios and fingerprints before and after editing (commands under
   [Bot scenarios and decision fingerprints](#bot-scenarios-and-decision-fingerprints)). Refactoring without
   logic changes must produce the same fingerprints. Intentional logic changes alter them; once scenarios pass
   and the change is accepted, save new fingerprints with `--tulis`.
3. Update the thesis notebooks in `../training/prethesis/ai_2_dataset_baru/` (`npc_fuzzy.ipynb`, `npc_nlg.ipynb`)
   so the report still describes the game. Required matches: logic (inputs, rules, overriding facts), calculations
   (curves, centroid, formulas), order, and function, variable, constant, parameter, and data-key names. Notebook
   code organization and placement may differ from the backend. Notebooks are no longer exported to the backend.
4. Update [GAME_CONCEPT.md](GAME_CONCEPT.md) if bot behavior changes, and affected panel menu 08 documentation
   (sources in `communicationfolder/`).

### Adding or changing a fuzzy system

1. Open its group file in `bot/fuzzy/`. Import any new group file in `bot/fuzzy/__init__.py`; that import order
   becomes the order of `SEMUA_SISTEM`.
2. Define the rule table as a constant `ATURAN_<NAMA>` immediately above the function: 3 rows × 3 columns of
   `"rendah"`, `"sedang"`, `"tinggi"`. Rows represent the first input's level; columns, the second input's level.
3. Decorate the function with `@sistem_fuzzy(ATURAN_<NAMA>, "one-sentence meaning")`. The function name becomes
   the system name; parameter names become input names shown in the panel (for example,
   `tekanan=tinggi DAN dukungan=rendah`, pressure=high AND support=low). The body only needs
   `return hitung("<nama>", input_pertama, input_kedua)`.

   Example from `bot/fuzzy/malam.py` (comments translated; identifiers and the panel description are preserved):

   ```python
   # Silence a townsperson who is rallying votes and poses a real threat to the Hitman.
   # Flow: 1 classify ancaman_sekarang and ancaman as low/medium/high -> 2 check rules -> 3 centroid -> 4 score 0–100
   ATURAN_GAG = [                        # rows = ancaman_sekarang, columns = ancaman (low, medium, high)
       ["rendah", "rendah", "rendah"],   # low ancaman_sekarang
       ["rendah", "sedang", "tinggi"],   # medium ancaman_sekarang
       ["sedang", "tinggi", "tinggi"],   # high ancaman_sekarang
   ]

   @sistem_fuzzy(ATURAN_GAG, "Membungkam penggalang suara yang memang berbahaya bagi Hitman.")
   def gag(ancaman_sekarang, ancaman):
       return hitung("gag", ancaman_sekarang, ancaman)
   ```

4. Call it in `bot/fuzzy_controller.py`. Divide its output by 100 before feeding it into another fuzzy system.
   Systems selected per candidate (chat, Gag, Peek) are called by name through `nilai_sistem(nama, input_kandidat)`.
5. Changing tables or curves changes bot behavior; changing the description only changes panel explanatory text.
   Both alter fingerprints, so follow [Changing bot logic](#changing-bot-logic).

## Coding style

### Formatters and lint

- Python: four spaces, Black and Ruff with a 100-character width (`pyproject.toml`). Ruff checks only unused
  imports and variables (`F401`, `F841`).
- TypeScript, JavaScript, HTML, JSON, and YAML: Prettier, two spaces, width 100. CSS/SCSS is not formatted.
- Dependencies, build output, lockfiles, local environments, user uploads, and binary models are not formatted.

```sh
npm install                                      # From root; also installs frontend dependencies
python -m pip install -r backend/requirements-dev.txt
npm run format          # Prettier + Black
npm run format:check
python -m ruff check backend
```

### Function and comment organization

- **Callees appear above their callers**, allowing files to be read from top to bottom.
- **Above a function:** a 1–2 sentence comment describing its purpose. For multi-step functions, add a numbered
  `Alur:` (Flow) line. A single-step function needs only its explanation. Example from
  `services/survey_service.py` (comments translated here):

  ```python
  # Save the new panel order (drag or ▲▼). The list contains every question, including inactive
  # ones, exactly once; positions are rewritten as 10, 20, 30, … in one transaction.
  # Flow: 1 reject duplicate IDs -> 2 read all IDs -> 3 reject unknown/missing IDs -> 4 write new positions
  def reorder_questions(self, daftar_id: list[int]):
  ```

  In long functions, numbered comments mark flow steps above the relevant lines (for example, `# 4 simpan`, save).
- **Module docstrings** explain file purpose and a numbered "Alurnya" (Flow), as in `bot/bot_controller.py`,
  `services/room_service.py`, and `services/chat_service.py`.
- In-function comments explain intent that is not obvious from code, such as storing before broadcasting,
  preventing stale responses, and checking private information.
- **Used once → inline it at the call site.** Separate functions or files are for code used in two or more places.
- New names and comments use Indonesian without abbreviations. Existing English names (for example, in the
  engine and models) are retained.
- Test names describe the scenario and expected result; test helpers prepare fake data without calling
  production services.
- Before deleting a symbol, check routes, template bindings, decorators, events, CLI/deployment entry points,
  and tests. Dynamic references (for example, `patch("app...")` or fuzzy system names in strings) may not appear
  as ordinary function calls.

## Accounts, sessions, and login

- **Registration:** usernames contain 3–40 letters, digits, or underscores; full names are 1–100 characters;
  passwords are 10–128 characters with confirmation. Passwords use PBKDF2-SHA256. Duplicate usernames are rejected,
  including usernames still recorded in `match_participants` or `survey_responses` (surveys are username-bound,
  so a new owner would inherit someone else's surveys). Registration immediately grants a session. The API still
  accepts email from older frontends but does not store it because ownership was never verified.
- **Display names** (`periksa_nama_tampilan` in `schemas/auth.py`, used by registration, profile, user panel, and
  Google names): trim edges; reject control/bidirectional characters, names with no letters/digits (for example,
  emoji only), or a first word that is a pronoun or game term never recognized as a name by NLU (`KATA_GANTI` and
  `ISTILAH_GAME` in `bot/nlu.py`, for example, "Aku", "Gw", "Vote"). Without a display name, apply the same
  rules to the username. Existing accounts with such names are unchanged; the Manajemen user (User Management)
  panel can rename them. Registration/profile forms first check the letter/digit requirement, then display
  server rejection reasons (`detail[].msg` in 422 responses); the forbidden-word list exists only on the server.
- **Login:** the form requests a username. The API also accepts Google-verified email, but Google accounts
  usually have no password and use the Google button. Missing, disabled, and Google-only accounts still perform
  PBKDF2 against a dummy hash, avoiding account-existence leaks through response timing. Player sessions last
  `AUTH_SESSION_HOURS` hours (default 24). Only token hashes are stored. Expired sessions are deleted in a
  separate transaction after successful login, registration, or Google login to prevent concurrent logins from
  deadlocking. Cleanup failure does not fail login.
- **Google:** Google Identity Services popup. The backend verifies signature, audience, issuer, expiry, verified
  email, and a one-use nonce (5 minutes). The nonce is HMAC-signed with a random process key and carries its own
  expiry, so `/google/challenge` does not fill memory; only used nonces are remembered. Login rebuilds the Google
  button with a fresh nonce once the old one is four minutes old (checked every 30 seconds and on tab focus),
  except while the window lacks focus because a Google popup may be open. Identity uses Google `sub`; existing
  accounts are never taken over through matching email. If the email remains attached to an old unverified
  identity (typed email from the former registration form), it is detached from that account and a new Google
  account is created. New Google accounts receive a random username and the token name if valid under display-name
  rules, otherwise "Detective". Google tokens are not stored.
- **Attempt limits** (`middleware/auth_limits.py`, in one worker's memory): player login, registration, and
  Google endpoints allow 60 per minute per client IP and endpoint, accommodating labs/campus Wi-Fi sharing an
  IP; panel login and writer checks allow 15 per minute. Incorrect passwords are counted per account (normalized
  username/email input): 10 within 15 minutes block that account from any IP; successful login clears the count.
  Locally, all players appear as the gateway IP and share its limit. On Azure, uvicorn uses `--proxy-headers`,
  so the IP comes from Caddy.
- **Profile:** the pencil icon saves name and username through `POST /api/auth/me`. Usernames can change only
  after leaving the room. Account ID and Google identity remain unchanged; archived chat sender names retain
  their values at send time.
- **Avatar:** 6 skins (`arthur`, `dexter`, `eloise`, `jenny`, `kiera`, `sadie`), saved through `PUT /api/auth/skin`
  (default `dexter`). In a match, a skin already used by an earlier entrant is replaced with a free skin;
  duplicates are allowed with more than 6 participants.
- **Panel user management** (`controllers/users.py`, `services/user_service.py`): add username/password accounts
  without creating sessions; edit names/usernames (rejected while in a room, revokes old sessions); reset passwords
  only for local accounts and revoke all their sessions; delete an account with username confirmation only after
  it has left the room. Only the account, login identities, and sessions are deleted; chat, Checker traces,
  participant archives, and survey answers remain. Deleted usernames with history therefore cannot be reused.
  The `scripts/create_user.py` CLI uses the same `RegisterRequest` validator and `create_user`, so its rules
  match the API.
- `ADMIN_USERNAMES` and `HISTORY_ADMIN_USERNAMES` in `.env` are only reserved-username lists (unavailable to game
  accounts). Bot names are also reserved.
- Self-service password reset, email verification for password accounts, and account linking are not implemented.

## Tests and simulations

### The `backend/tests/` structure

| Location | Contents |
| --- | --- |
| `test_*.py` | Unit and integration tests, run by `unittest discover` |
| `test_skenario_fuzzy.py` | 328 labeled notebook scenarios: the reference for bot reasoning behavior |
| `test_skenario_nlg.py` | Payloads, rule checks, per-type templates, and writer prompts, without LLM or IndoBERT |
| `palsu/` | Test fakes: `arsip_palsu.py` (bot archives), `socket_palsu.py` (Socket.IO), `nlu_palsu.py` (fast IndoBERT replacement requiring no model files) |
| `jejak/` | `rekam_jejak.py` and `sidik.json`: bot decision fingerprints with fixed seeds |
| `simulasi/` | `simulasi_keseimbangan.py` and `uji_ab_vote.py`: bot-versus-bot matches |
| `panel_ui.test.mjs` | Panel UI tests with jsdom |
| `live_match_smoke.py`, `live_auth_smoke.py`, `mysql_smoke.py` | Manual tools touching real servers/databases; excluded from `test_*.py` |

Automated tests cover 4–10 players and compositions, the Syndicate (shared Hostage/Gag, teammate targeting
restrictions, teammate privacy, remaining-Hitman announcements), matches still without winners after round 25,
Guard, Peek, Gag, Hostage, Tribunal extensions, Spy allies, team chat and its privacy, victory, snapshot privacy,
voting, reconnects, bot scheduling, LLM writers/template fallback with fake models, preparation screens, surveys,
and full multi-bot matches against the real engine. Tests do not establish tactical quality or production-provider
latency, nor prove that external AI connections are currently active.

### Running tests

Host Python usually lacks backend dependencies, so the easiest route is through running containers
(from the repository root):

```sh
docker compose exec -T ai-engine python -m unittest discover -s tests -p "test_*.py" -v
docker compose exec -T frontend npm test -- --watch=false
docker compose exec -T frontend npm run build
node --test backend/tests/panel_ui.test.mjs      # From root; requires frontend/node_modules
```

With your own virtual environment (`pip install -r backend/requirements-dev.txt`), run the suite from `backend`:
`python -m unittest discover -s tests -p "test_*.py"`. Tests requiring MySQL fail to connect without a database.

### Bot scenarios and decision fingerprints

Run from `backend` before and after changing or refactoring bot code:

```sh
python -m unittest tests.test_skenario_fuzzy tests.test_skenario_nlg
python tests/jejak/rekam_jejak.py --cek
```

`rekam_jejak.py` records three parts, each with its own fingerprint: (a) all `putuskan` results in 4–10-bot rooms,
(b) template dialogue, LLM prompts, and team chat, (c) one full bot step through `BrainRuntime.langkah` with fake
NLU. Options: no option prints fingerprints; `--cek` compares with `sidik.json` (exit 1 on differences);
`--tulis` saves new fingerprints; `--simpan FOLDER` writes full traces to investigate differences.

### Manual tests against a server or database

```sh
# Real match with 6 temporary QC accounts until town wins; only test-owned accounts are cleaned up.
docker compose exec -T ai-engine python -m tests.live_match_smoke

# Only for a temporary MySQL database with migrations applied (this test writes data).
STRUCTURE_TEST_DB=1 python -m unittest discover -s tests -p mysql_smoke.py -v
```

Do not run tests that write data against a user database or public deployment.

### Balance simulation and A/B testing

Two scripts in `tests/simulasi/` play all-bot matches (fuzzy brains, perfect NLU labels from sender plans)
against the actual engine. Run from `backend`; the first argument is the backend folder (`.`).

```sh
# <games per cell> <decision steps per phase> <size:hitman/spy/stalker> ...
python tests/simulasi/simulasi_keseimbangan.py . 200 6 "7:2/2/1" "8:2/2/1"

# Forced voting when town is critical, enabled vs disabled: <games> <steps per phase> [players, default 6]
python tests/simulasi/uji_ab_vote.py . 200 6 7
```

Output includes town win rate ± 95% CI, average rounds, matches without winners, and illegal actions (the A/B
test also reports town vote accuracy). Fixed seeds make results repeatable. Both scripts use at most half the
CPU cores; `SIM_PROSES` can lower this further. Latest results are recorded in
[GAME_CONCEPT.md](GAME_CONCEPT.md#composition-balance).

## Implementation limits

- Lobbies, engine, roles, actions, votes, timers, and bot memory live in **one backend process**. Browser reloads
  or reconnects restore the snapshot and latest 100 messages while that process lives. Restarting/recreating
  the backend clears active matches; MySQL chat archives and traces remain but cannot restore matches.
- Do not run multiple backend workers before shared state exists. Rooms, the Google nonce key, and all attempt
  limits (login, room joins, chat) exist in only one process.
- All rooms share two `BrainRuntime` thread groups: **one brain thread** (`eksekutor_keputusan`) for every bot's
  reasoning step and IndoBERT reads of every chat message, because bot memory is not designed for parallel access;
  and **six writer threads** (`eksekutor_nlg`) for bot dialogue. Panel simulation uses separate threads (one
  reasoning, two writers); IndoBERT inference remains serialized by the NLU memo lock. On the production VM
  (2 vCPUs), a 10-player room makes IndoBERT take about 8.85 seconds per message on average, so queued bot steps
  may exceed `BATAS_LANGKAH_DETIK` (25 seconds) and be canceled. Measurements are in the Proses AI (AI Process)
  web document, section 2, *Lama tiap tahap* (Stage Durations), and queues are visible live in Checker.
- Offline players are not automatically replaced.
