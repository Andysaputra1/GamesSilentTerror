Alur utama main.py

Alur utama main.py✅ sudah dibahas

backend/app/main.py adalah titik masuk backend. File ini merakit semua bagian: server HTTP, Socket.IO untuk chat realtime, bot NPC, dan jam permainan.

Alur

[SETUP LOGGER] -> [KONEK SOCKET] -> [SIAPKAN BOT NPC] -> [KONEK API] -> [CORS]
  -> [ROUTES CONTROLLER] -> [GABUNG API + SOCKET] -> [SERVER NYALA] -> [SERVER MATI]
TahapGunanyaKapan jalan
[SETUP LOGGER]Menyiapkan pencatat log serverSaat file diimpor
[KONEK SOCKET]Membuat jalur realtime dengan browser dan mendaftarkan event-nyaSaat file diimpor
[SIAPKAN BOT NPC]Membuat pengatur botSaat file diimpor
[KONEK API]Membuat aplikasi FastAPISaat file diimpor
[CORS]Mengatur alamat web mana yang boleh memanggil APISaat file diimpor
[ROUTES CONTROLLER]Mendaftarkan semua alamat APISaat file diimpor
[GABUNG API + SOCKET]Menyatukan API dan Socket.IO jadi satu aplikasiSaat file diimpor
[SERVER NYALA]Mengecek MySQL, memuat konfigurasi, memuat otak AI, menyalakan jamSaat Uvicorn menyala
[SERVER MATI]Menghentikan jam dan bot, lalu menutup koneksiSaat Uvicorn mati

Yang tidak terlihat dari kode

  • [SERVER NYALA] dan [SERVER MATI] ditulis paling atas di file, di dalam lifespan. Keduanya baru jalan saat Uvicorn menyala dan mati, jadi urutannya tetap di belakang.

main.py / [KONEK SOCKET]

2[KONEK SOCKET]✅ sudah dibahas

Membuat jalur yang tetap terbuka antara server dan browser. Lewat jalur ini server bisa mengirim chat kapan saja, tanpa browser harus bertanya berulang.

Alur

Waktu 1, saat server dirakit (sekali):
  Buat server Socket.IO
    -> [[settings.allowed_origins]]  ambil daftar alamat web yang boleh konek
    -> [[SocketGameController]]  buat pengendali, catatan socket masih kosong
    -> daftarkan 3 event: [[connect]], [[disconnect]], [[send_chat]]

Waktu 2, saat pemain main (berulang):
  Browser tersambung  -> [[connect]]     cek token dan room, catat socket, masuk kanal room
  Pemain kirim chat   -> [[send_chat]]   cek pesan, simpan, kirim ke semua orang di room
  Browser terputus    -> [[disconnect]]  hapus catatan socket

Kode

Yang dipakai dari sio (server Socket.IO)
PemanggilanGunanya
sio.on("connect", fungsi)Mendaftarkan fungsi untuk sebuah event
sio.enter_room(sid, "ABC")Memasukkan satu sambungan ke kanal room
sio.leave_room(sid, "ABC")Mengeluarkan sambungan dari kanal room
sio.emit("receive_chat", data, to="ABC")Mengirim pesan ke semua sambungan di room itu
sio.emit("system_alert", data, to=sid)Mengirim pesan ke satu sambungan saja
Contoh: pemain bernama Budi
KejadianYang terjadi di server
Budi membuka game[[connect]] mengecek token dan room ABC, mencatat sambungan s1 = Budi, lalu memasukkan s1 ke kanal ABC
Budi mengirim "halo"[[send_chat]] melihat catatan s1, menyimpan pesan, lalu mengirimnya ke semua orang di kanal ABC
Budi menutup tab[[disconnect]] menghapus catatan s1. Budi tetap anggota room ABC dan bisa menyambung lagi

Yang tidak terlihat dari kode

  • async_mode="asgi" membuat server ini bisa digabung dengan FastAPI di [GABUNG API + SOCKET].
  • Chat bot tidak lewat [[send_chat]]. Bot hanya memakai [[emit_room]] untuk mengirim pesannya ke room.
Sudah digabung register_socket_handlers dihapus karena hanya dipakai di main.py. Pendaftaran event kini terlihat langsung di tahap ini.

main.py / [KONEK SOCKET] / connect / auth_service.check_user_by_token

2.3.1auth_service.check_user_by_token✅ sudah dibahas

Mengubah token dari browser menjadi data akun.

Alur

Terima token dari connect
  -> token kosong?
       \> ya: tolak ("Sesi login tidak ditemukan.")
  -> jalankan_transaksi:
       -> [[SessionLocal]]  buka sesi DB
       -> [[auth_queries.account_by_token]]  cari akun, memakai hash token dan waktu UTC sekarang
       -> commit
            \> DB error: rollback, catat di log, tolak ("Layanan login sedang tidak tersedia.")
       -> tutup sesi, baik berhasil maupun gagal
  -> akun tidak ketemu?
       \> ya: tolak ("Sesi login sudah tidak valid.")
  -> kembalikan data akun: id, username, display_name, skin_id

Kode

Yang tidak terlihat dari kode

  • DB hanya menyimpan hash token, jadi token asli tidak terbaca walau DB bocor.
  • AuthenticatedUser(**akun) mengisi field sesuai nama kolom hasil query.
  • Pesan tolak berhenti di [[connect]]. Browser hanya menerima "Login diperlukan."
Risiko Rumus hash ditulis langsung di 4 tempat atas permintaan user: login, fungsi ini, dan logout di auth_service.py, serta issue_session di controller/api/auth.py. Kalau satu diubah sendiri, token yang sah tidak ketemu di DB dan pemain tertolak.

2.3.1.1SessionLocal✅ sudah dibahas

Bukan fungsi biasa, tapi pembuat sesi DB. Disiapkan sekali saat file diimpor, lalu dipanggil tiap kali butuh sesi.

Alur

Saat file diimpor (sekali):
  [[settings.sqlalchemy_database_url]]  ambil alamat DB
  -> buat engine: kumpulan koneksi (pool) yang dipakai bersama
       \> koneksi yang sudah diputus MySQL diganti otomatis

Saat SessionLocal() dipanggil (tiap kali butuh):

  -> koneksi baru diambil dari pool saat query pertama jalan
  -> database.close() mengembalikan koneksi ke pool, tidak memutusnya

main.py / [KONEK SOCKET] / send_chat

2.5send_chatbelum dibahas

Jalan saat pemain mengirim chat, lewat 5 tahap. Di akhir, jejak pesan selalu dicatat, walau chat berhenti di tengah.

Alur

Mulai hitung waktu

  TAHAP 1, cek isi dan identitas
    data berupa dict dan message berupa teks?
    -> rapikan pengirim dan pesan, panjang pesan harus 1-1000 karakter
    -> [[_verifikasi_socket]]  sambungan masih sah
         \> gagal di mana pun: system_alert ke pengirim, berhenti

  TAHAP 2, engine mengizinkan?
    Kunci room_service.lock
    -> ada pertandingan: [[Match.tick]] -> [[Match.can_chat]] -> simpan penanda fase
    -> tidak boleh chat: [[activity.record]] rejected, system_alert, berhenti
    -> [[checker_service.begin]]  buat jejak pesan
    -> [[activity.record]]  received

  TAHAP 3, simpan
    Kunci room_service.lock lagi
    -> room atau pertandingan sudah berganti? ValueError
    -> [[Match.tick]]  fase berubah atau tidak boleh chat lagi? ValueError
    -> [[PersistenceService.record_player_message]]  simpan ke MySQL
    -> ada pertandingan: [[Match.add_message]]  masuk daftar chat pertandingan
         \> ValueError atau PersistenceError: catat di jejak, system_alert, berhenti

  TAHAP 4, kirim
    [[emit_room]]  siarkan receive_chat ke kanal room

  TAHAP 5, baca
    Ada pertandingan: [[catat_nlu]]  IndoBERT membaca pesan

  Selesai atau berhenti di tengah, kalau jejak sudah ada:
    durasi -> [[PersistenceService.record_trace]]
         \> gagal: catat di log saja

Kode

Yang tidak terlihat dari kode

  • Tahap 3 mengecek ulang karena aksi lewat HTTP bisa berjalan bersamaan. Di antara tahap 2 dan 3, pemain bisa saja kena Gag atau fase bisa berganti.
  • Match.tick dipanggil dulu karena jam baru berdetak tiap 0,5 detik, jadi fase bisa belum terbarui.
  • Di lobby tidak ada pertandingan. Chat tetap disimpan dan disiarkan, tanpa pengecekan engine dan tanpa IndoBERT.
Temuan Tahap 3 menulis ke MySQL sambil memegang room_service.lock, dan lock itu satu untuk semua room. Ini disengaja supaya Gag atau fase baru tidak diterobos, tapi operasi room lain menunggu selama itu. Durasinya belum diukur.
