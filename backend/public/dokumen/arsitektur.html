03Arsitektur yang dipakai, dan kenapa

"Arsitektur" artinya cara aplikasi dipotong menjadi bagian-bagian dan cara bagian itu saling bicara. Silent Terror memakai beberapa pola yang umum dipakai aplikasi web. Setiap kartu berisi artinya, lalu alasannya tepat di bawahnya.

🔁 Client–server

Browser (client) hanya menampilkan dan mengirim permintaan; server memegang aturan dan data.

Kenapa dipilih: Game ini berisi rahasia (role). Kalau aturan ada di browser, pemain bisa mengintip atau curang lewat DevTools.

🧩 Single Page Application (Angular)

Seluruh tampilan dimuat sekali; pindah halaman tidak memuat ulang situs, hanya mengganti isi layar.

Kenapa dipilih: Pergantian layar (lobby → persiapan → meja) terasa instan, dan file statisnya cukup dihosting di Vercel.

📨 REST API (HTTP + JSON)

Setiap permintaan punya alamat dan metode (GET membaca, POST/PUT mengubah). Jawabannya teks JSON.

Kenapa dipilih: Mudah diuji, mudah diamankan per alamat (siapa boleh apa), dan dipahami semua bahasa pemrograman.

⚡ WebSocket (Socket.IO) untuk chat

Sambungan yang tetap terbuka sehingga server bisa mendorong chat baru ke semua pemain seketika.

Kenapa dipilih: Chat harus terasa langsung. Status permainan lain cukup dengan polling HTTP tiap detik yang lebih sederhana dan tahan putus.

🔒 Server-authoritative + snapshot privat

Engine Match di backend memvalidasi setiap aksi dan membuat snapshot berbeda untuk setiap pemain.

Kenapa dipilih: Mencegah kebocoran informasi tersembunyi dan aksi ganda; frontend tidak perlu dipercaya.

🧱 Backend berlapis

controller (pintu masuk) → services (aturan) → models (SQL) → module (koneksi). Socket punya controller sendiri.

Kenapa dipilih: Setiap lapisan punya satu tugas, jadi mudah diuji dan diubah tanpa merusak lapisan lain.

🧠 State pertandingan di memori, arsip di MySQL

Room dan pertandingan yang sedang berjalan disimpan di memori satu proses; chat, jejak, akun, dan survei disimpan ke database.

Kenapa dipilih: Permainan cepat (tanpa query di setiap tick). Konsekuensinya: restart backend menghapus pertandingan yang sedang berjalan, jadi server dijalankan dengan satu worker.

📓 Otak bot hasil ekspor notebook

Logika bot ditulis dan diuji di notebook skripsi, lalu diekspor otomatis ke services/npc_brain/generated/.

Kenapa dipilih: Kode yang diuji di penelitian sama persis dengan yang dipakai di game.

04Cara kerja API (untuk yang belum pernah membuatnya)

📮
API seperti loket. Browser menulis formulir (request), menyebut loketnya (alamat), menunjukkan gelang tiket (token login), lalu menyerahkannya. Server membalas dengan nomor status (berhasil atau ditolak) dan isi jawaban dalam format JSON.

Gelang tiket: token login

  1. Saat login berhasil, server membuat token acak 32 byte. Yang disimpan di database hanya hash SHA-256-nya, jadi pencuri database tidak bisa memakai tokennya.
  2. Browser menyimpan token di localStorage dan mengirimnya di setiap request: Authorization: Bearer <token>.
  3. Setiap endpoint pemain memeriksa token lewat require_authenticated_user; endpoint admin memakai sesi panel terpisah (require_panel, berlaku 8 jam).
  4. Logout mencabut token di server. Token yang kedaluwarsa (bawaan 24 jam) ditolak dengan 401.

Dua cara browser mendapat kabar baru

🔄 Polling HTTP

Halaman bertanya berkala: lobby tiap 3 detik (GET /api/rooms/{code}), meja permainan tiap 1 detik (GET /api/rooms/{code}/game), dan aplikasi tiap 3 detik mencari pertandingan aktif.

Kenapa dipilih: Tahan koneksi putus dan selalu memperbaiki dirinya sendiri: jawaban berikutnya pasti snapshot terbaru.

📣 Push Socket.IO

Saat ada chat baru, server langsung mengirim event receive_chat ke semua browser di room.

Kenapa dipilih: Chat tampil tanpa menunggu polling berikutnya.

05Frontend: dari umum ke khusus

Frontend dipecah menjadi kerangka, halaman, komponen bersama, dan service; lalu setiap fitur ditelusuri sampai keluarannya.

Umum: apa yang terjadi saat situs dibuka

  1. Browser mengunduh file statis (HTML, JavaScript, CSS, gambar) dari Vercel.
  2. Layar loading langsung tampil (meja kayu, papan judul, barisan karakter) sambil font dan gambar utama diunduh.
  3. Sekali per tab muncul ajakan layar penuh. Browser hanya mengizinkan layar penuh dari klik pemain, jadi ini ajakan, bukan paksaan.
  4. Router memilih halaman sesuai alamat, setelah guard memeriksa sesi login dan pertandingan aktif.
  5. Halaman meminta data ke backend lewat service, lalu menampilkannya. Aturan permainan tidak pernah dihitung di sini: browser hanya menggambar "foto" (snapshot) yang dikirim server dan mengirim pilihan pemain.

Bagian-bagian frontend

Frontend (Angular 21, frontend/src/app) terbagi empat. Halaman tidak pernah memanggil backend sendiri: semua lewat service, dan semua service memakai alamat backend dan header token yang sama.

Kerangka aplikasi

Yang berjalan sekali saat situs dibuka dan selalu ada di belakang semua halaman.

  • App: Komponen akar: wadah halaman (router-outlet), undangan layar penuh, penyala layar loading, pemantau logout antartab, dan pemantau pertandingan aktif tiap 3 detik.
  • app.routes.ts: Daftar alamat dan halaman yang dibuka, beserta guard-nya.
  • app.config.ts: Fasilitas Angular: router (chunk game diunduh di latar setelah halaman pertama), HttpClient, dan hydration.
  • BootLoader: Layar loading awal.
  • FullscreenInvite: Undangan layar penuh sekali per tab.

Halaman (features/)

Satu folder per layar. Halaman hanya menampilkan dan mengirim permintaan; keputusan permainan selalu dari backend.

  • Auth: /login: Log In, Register (daftar), Google, status server, hitung mundur.
  • MainPage: /main: kartu role + skin, ganti skin, buat/gabung room, panduan meja, pengingat survei.
  • Lobby: /lobby: ruang tunggu, kode room, roster, bot, mulai.
  • Game: /game: persiapan, meja, chat, aksi, vote, layar akhir, survei.
  • PanelRedirect: /panel: meneruskan ke panel admin milik backend.

Komponen bersama (core/)

Potongan tampilan yang dipakai lebih dari satu halaman.

  • ProfileMenu: Menu akun di Main, Lobby, dan Game: ubah nama/username, logout.
  • SurveyForm: Formulir survei di layar akhir dan di pengingat Main.
  • RoleRevealCard: Kartu role pratinjau dengan skin dan properti role di Main.
  • SurveyReminder: Pengingat survei yang belum diisi (di Main).
  • FullscreenPrompt: Tombol masuk/keluar layar penuh di HUD game.

Service dan alat umum (core/, shared/)

Kode tanpa tampilan yang dipakai banyak halaman: semua request ke backend lewat sini.

  • SessionService: Profil, skin, logout.
  • RoomService: Request room/lobby.
  • GameService: Snapshot dan aksi permainan, keluar, survei.
  • ActiveMatchService: Mencari pertandingan aktif akun (pemulihan).
  • AssetPreloader: Mengunduh gambar sebelum dipakai.
  • storage.ts, backend-url.ts, room-helpers.ts: Kunci penyimpanan, header token, alamat backend, cek kode room.
  • authGuard, loginRedirectGuard, activeMatchGuard: Penjaga pintu halaman.

06Backend: dari umum ke khusus

Backend dipecah per pintu (HTTP, socket, jam), per service, dan per aturan permainan, masing-masing dari masukan sampai keluarannya.

Umum: satu program, dua pintu

Backend adalah satu program Python yang menjalankan FastAPI (REST API) dan Socket.IO (chat) di port yang sama, dengan satu worker karena room dan pertandingan disimpan di memori proses itu.

  • Saat menyala (lifespan()): model SVM lama dimuat (cadangan NLU), koneksi MySQL dicek, konfigurasi AI dan konfigurasi otak NPC dari panel dimuat, otak bot (IndoBERT + tiga metode) mulai dimuat di latar agar server langsung melayani, lalu jam permainan dinyalakan.
  • Jam permainan: tugas asyncio yang berulang selamanya: room_service.tick_all(), npc_service.schedule(), tidur 0,5 detik. Error satu putaran dicatat dan tidak mematikan jam.
  • Satu port, dua protokol: objek yang dijalankan uvicorn adalah socketio.ASGIApp(sio, other_asgi_app=app): request Socket.IO ditangani sio, sisanya diteruskan ke FastAPI.
  • Saat berhenti: jam dibatalkan, task bot dihentikan, thread otak ditutup, pool database dilepas.

10Di mana semuanya berjalan (deployment)

frontend / browserbackenddatabaseAI botlayanan luar

Vercel

Menyimpan dan menyebarkan file frontend. Setiap push ke cabang main di GitHub otomatis dibangun ulang dan diterbitkan.

VM Azure

Tiga container Docker: proxy (Caddy, HTTPS otomatis, satu-satunya yang membuka port 80/443), backend, dan mysql (data di volume). Pembaruan: git pull, migrasi baru, lalu docker compose up -d --build backend.

Laptop ai-docker

Ollama (Qwen3) di balik gerbang nginx yang meminta token, dibuka ke internet lewat Cloudflare tunnel. Linknya dikirim ke backend lewat API panel setiap kali dinyalakan.

OpenRouter

Layanan LLM di cloud. Bila semua penulis LLM gagal, bot tetap bicara memakai kalimat templat.

Jangan restart backend saat ada pertandingan: pertandingan yang sedang berjalan ada di memori dan akan hilang. Arsip (chat, jejak, survei) tetap tersimpan.
