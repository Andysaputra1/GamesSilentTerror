00Cara membaca dokumen ini

Dokumen ini menjelaskan cara kerja aplikasi Silent Terror dari yang paling umum sampai yang paling rinci. Bab 01–04 bisa dibaca tanpa latar belakang pemrograman. Bab 05–09 masuk ke frontend, backend, data, dan server. Bab 10 menelusuri kejadian penting langkah demi langkah. Bab 12 (paling bawah) berisi diagram UML: use case, class, state, activity, flowchart, sequence, dan deployment.

🖥️ Frontend

Bagian yang dilihat dan disentuh pemain di browser: halaman login, menu utama, lobby, dan meja permainan.

⚙️ Backend

Program di server yang memegang aturan permainan, menyimpan data, dan menjalankan bot AI. Browser hanya bertanya dan menampilkan jawabannya.

🗄️ Database

Arsip permanen (MySQL): akun, chat, jejak keputusan bot, dan survei.

🤖 Bot AI

Pemain komputer yang membaca chat, menimbang bukti, lalu bicara dan memilih. Cara kerjanya dijelaskan rinci di dokumen Proses AI (menu panel 08).

Tabel endpoint, event realtime, halaman, kunci penyimpanan browser, daftar file, dan tabel database di dokumen ini dibaca langsung dari kode saat dokumen dibangun, jadi isinya sama dengan yang berjalan di server.

01Gambaran besar dalam satu menit

🍽️
Bayangkan sebuah restoran. Ruang makan dan menu adalah frontend: yang dilihat tamu. Dapur adalah backend: di sana aturan dijalankan dan keputusan dibuat. Buku besar di kantor adalah database. Pelayan yang bolak-balik membawa pesanan adalah API. Koki tamu yang ikut duduk di meja sebagai pemain adalah bot AI.

Saat pemain membuka situs, browser mengambil file halaman dari Vercel (1). Setelah itu semua pertanyaan dan aksi (login, buat room, chat, vote) dikirim ke server Azure (2). Di server, Caddy memberi HTTPS lalu meneruskan ke backend Python. Backend menyimpan arsip di MySQL, dan untuk menulis kalimat bot ia meminta bantuan LLM di OpenRouter atau di laptop pengembang lewat ai-docker.

Satu prinsip yang paling penting: server yang memutuskan. Browser tidak pernah tahu role pemain lain dan tidak bisa mengubah hasil permainan. Setiap pemain menerima "foto" permainan (snapshot) yang hanya berisi hal yang boleh ia ketahui.

02Siapa memakai sistem ini

🙂 Pemain

Membuat akun, memilih skin, membuat atau bergabung ke room, lalu bermain: chat, aksi malam sesuai role, vote, dan mengisi survei di akhir.

👑 Host

Pemain yang membuat room. Hanya host yang boleh memilih kapasitas, menambah bot, dan menekan Mulai.

🤖 Bot NPC

Mengisi kursi kosong. Setiap bot punya ingatan, metode (Fuzzy, Utility AI, atau Behavior Tree), dan gaya bicara sendiri.

🛠️ Administrator

Masuk ke panel /panel dengan login terpisah: mengatur AI, memantau jejak bot, melihat riwayat chat, mengelola user dan survei, menjalankan simulasi, dan membuka dokumen.

⏱️ Jam server

Bukan orang: pengatur waktu di backend yang berjalan setiap 0,5 detik untuk mengganti fase dan menjalankan bot, walaupun semua tab pemain tertutup.

03Arsitektur yang dipakai, dan kenapa

"Arsitektur" artinya cara aplikasi dipotong menjadi bagian-bagian dan cara bagian itu saling bicara. Silent Terror memakai beberapa pola yang umum dipakai aplikasi web. Setiap kartu berisi artinya, lalu alasannya tepat di bawahnya.

🔁 Client–server

Browser (client) hanya menampilkan dan mengirim permintaan; server memegang aturan dan data.

Kenapa dipilih: Game ini berisi rahasia (role). Kalau aturan ada di browser, pemain bisa mengintip atau curang lewat DevTools.

🧩 Single Page Application (Angular)

Seluruh tampilan dimuat sekali; pindah halaman tidak memuat ulang situs, hanya mengganti isi layar.

Kenapa dipilih: Pergantian layar (lobby → persiapan → meja) terasa instan, dan file statisnya cukup dihosting di Vercel.

📨 REST API (HTTP + JSON)

Setiap permintaan punya alamat dan metode (GET membaca, POST/PUT mengubah). Jawabannya teks JSON.

Kenapa dipilih: Mudah diuji, mudah diamankan per alamat (siapa boleh apa), dan dipahami semua bahasa pemrograman.

⚡ WebSocket (Socket.IO) untuk chat

Sambungan yang tetap terbuka sehingga server bisa mendorong chat baru ke semua pemain seketika.

Kenapa dipilih: Chat harus terasa langsung. Status permainan lain cukup dengan polling HTTP tiap detik yang lebih sederhana dan tahan putus.

🔒 Server-authoritative + snapshot privat

Engine Match di backend memvalidasi setiap aksi dan membuat snapshot berbeda untuk setiap pemain.

Kenapa dipilih: Mencegah kebocoran informasi tersembunyi dan aksi ganda; frontend tidak perlu dipercaya.

🧱 Backend berlapis

controller (pintu masuk) → services (aturan) → models (SQL) → module (koneksi). Socket punya controller sendiri.

Kenapa dipilih: Setiap lapisan punya satu tugas, jadi mudah diuji dan diubah tanpa merusak lapisan lain.

🧠 State pertandingan di memori, arsip di MySQL

Room dan pertandingan yang sedang berjalan disimpan di memori satu proses; chat, jejak, akun, dan survei disimpan ke database.

Kenapa dipilih: Permainan cepat (tanpa query di setiap tick). Konsekuensinya: restart backend menghapus pertandingan yang sedang berjalan, jadi server dijalankan dengan satu worker.

📓 Otak bot hasil ekspor notebook

Logika bot ditulis dan diuji di notebook skripsi, lalu diekspor otomatis ke services/npc_brain/generated/.

Kenapa dipilih: Kode yang diuji di penelitian sama persis dengan yang dipakai di game.

04Cara kerja API (untuk yang belum pernah membuatnya)

📮
API seperti loket. Browser menulis formulir (request), menyebut loketnya (alamat), menunjukkan gelang tiket (token login), lalu menyerahkannya. Server membalas dengan nomor status (berhasil atau ditolak) dan isi jawaban dalam format JSON.

Gelang tiket: token login

  1. Saat login berhasil, server membuat token acak 32 byte. Yang disimpan di database hanya hash SHA-256-nya, jadi pencuri database tidak bisa memakai tokennya.
  2. Browser menyimpan token di localStorage dan mengirimnya di setiap request: Authorization: Bearer <token>.
  3. Setiap endpoint pemain memeriksa token lewat require_authenticated_user; endpoint admin memakai sesi panel terpisah (require_panel, berlaku 8 jam).
  4. Logout mencabut token di server. Token yang kedaluwarsa (bawaan 24 jam) ditolak dengan 401.

Dua cara browser mendapat kabar baru

🔄 Polling HTTP

Halaman bertanya berkala: lobby tiap 3 detik (GET /api/rooms/{code}), meja permainan tiap 1 detik (GET /api/rooms/{code}/game), dan aplikasi tiap 3 detik mencari pertandingan aktif.

Kenapa dipilih: Tahan koneksi putus dan selalu memperbaiki dirinya sendiri: jawaban berikutnya pasti snapshot terbaru.

📣 Push Socket.IO

Saat ada chat baru, server langsung mengirim event receive_chat ke semua browser di room.

Kenapa dipilih: Chat tampil tanpa menunggu polling berikutnya.

05Frontend: dari umum ke khusus

Umum: apa yang terjadi saat situs dibuka

  1. Browser mengunduh file statis (HTML, JavaScript, CSS, gambar) dari Vercel.
  2. Layar loading langsung tampil (meja kayu, papan judul, barisan karakter) sambil font dan gambar utama diunduh. Layar ini hilang begitu halaman pertama siap, paling lama 4 detik.
  3. Sekali per tab muncul ajakan layar penuh. Browser hanya mengizinkan layar penuh dari klik pemain, jadi ini ajakan, bukan paksaan.
  4. Router memilih halaman sesuai alamat, setelah guard memeriksa sesi login dan pertandingan aktif.
  5. Halaman meminta data ke backend lewat service, lalu menampilkannya. Aturan permainan tidak pernah dihitung di sini.

06Backend: dari umum ke khusus

Umum: satu program, dua pintu

Backend adalah satu program Python yang menjalankan FastAPI (REST API) dan Socket.IO (chat) di port yang sama, dengan satu worker karena room dan pertandingan disimpan di memori proses itu.

Lapisan dan tugasnya

frontend / browserbackenddatabaseAI botlayanan luar

controller/api

Memvalidasi bentuk request (Pydantic), memeriksa token, memanggil service, dan menerjemahkan error menjadi status HTTP.

realtime

Socket.IO: memeriksa token saat tersambung, memeriksa hak chat, menyimpan, lalu menyiarkan pesan ke room.

services

Aturan aplikasi: engine permainan, lobby, akun, survei, jejak, dan penjadwal bot. Transaksi database diatur di sini.

models

SQL langsung dengan parameter (:nama), tidak pernah menempelkan input pengguna ke teks SQL.

module

Infrastruktur: pool koneksi MySQL dan klien HTTP ke OpenRouter/Ollama.

services/npc_brain

Otak bot: IndoBERT, Fuzzy, Utility AI, Behavior Tree, dan NLG. Dijelaskan penuh di dokumen Proses AI.

Khusus: engine permainan (services/match_engine.py)

Engine tidak tahu apa pun tentang HTTP, socket, atau database. Ia hanya menyimpan keadaan satu pertandingan dan menolak aksi yang melanggar aturan. Komposisi role dan durasi fase (standar, detik) mengikuti jumlah peserta:

  • Aksi: act() memeriksa role, fase, target hidup, larangan menarget rekan Syndicate, cooldown Gag dan Peek, serta aturan Guard dua malam berturut-turut. vote() hanya saat Tribunal dan hanya sekali.

Khusus: lobby dan jam (room_service.py, main.py)

Semua operasi room memakai satu RLock agar dua request bersamaan tidak menggandakan aksi. Jam di main.py berjalan tiap 0,5 detik: tick_all() memajukan fase setiap room, lalu NPCService.schedule() menjadwalkan langkah bot. Persiapan menunggu AI siap, minimal 10 detik baca, dan semua kartu dibuka (pemain yang belum membuka ditunggu 15 detik; total paling lama 90 detik).

Khusus: keamanan

Password

Disimpan sebagai PBKDF2-SHA256 600.000 putaran dengan salt acak; tidak pernah disimpan asli.

Batas percobaan

Login, daftar, Google, dan login panel dibatasi 15 percobaan per menit per IP per alamat. IP pemain dibaca dari header Caddy (uvicorn --proxy-headers).

Login Google

Token Google diverifikasi di backend bersama nonce sekali pakai; email yang sama tidak otomatis mengambil alih akun lain.

Rahasia

API key OpenRouter dan token tunnel disimpan terenkripsi (Fernet) dan tidak pernah dikirim kembali ke browser.

Panel & dokumen

Halaman panel dan dokumen memakai Content-Security-Policy; dokumen dibuka dalam sandbox sehingga skripnya tidak bisa membaca data panel.

CORS

Hanya origin frontend resmi yang boleh memanggil API dan Socket.IO dari browser.

08Data: apa yang di memori, apa yang di database

Room yang terbuka, pertandingan yang sedang berjalan (role, aksi, vote, 100 chat terakhir), ingatan setiap bot, jejak live 50 room terbaru, dan batas percobaan login.

Akun dan sesi, semua chat beserta bacaan IndoBERT, jejak keputusan bot, konfigurasi panel, survei, dan metode bot per pertandingan.

Kenapa dipilih: Data penelitian (chat, jejak, survei) tidak boleh hilang walau server dinyalakan ulang.

Token login, profil singkat, dan pointer room tab ini.

Kenapa dipilih: Agar login dan pemulihan room tidak perlu ditanyakan ulang setiap pindah halaman.

09Di mana semuanya berjalan (deployment)

frontend / browserbackenddatabaseAI botlayanan luar

Vercel

Menyimpan dan menyebarkan file frontend. Setiap push ke cabang main di GitHub otomatis dibangun ulang dan diterbitkan.

VM Azure

Tiga container Docker: proxy (Caddy, HTTPS otomatis, satu-satunya yang membuka port 80/443), backend, dan mysql (data di volume). Pembaruan: git pull, migrasi baru, lalu docker compose up -d --build backend.

Laptop ai-docker

Ollama (Qwen3) di balik gerbang nginx yang meminta token, dibuka ke internet lewat Cloudflare tunnel. Linknya dikirim ke backend lewat API panel setiap kali dinyalakan.

OpenRouter

Layanan LLM di cloud. Bila semua penulis LLM gagal, bot tetap bicara memakai kalimat templat.

Jangan restart backend saat ada pertandingan: pertandingan yang sedang berjalan ada di memori dan akan hilang. Arsip (chat, jejak, survei) tetap tersimpan.
