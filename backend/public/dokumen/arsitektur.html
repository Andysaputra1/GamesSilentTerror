4Arsitektur yang dipakai, dan kenapa

"Arsitektur" artinya cara aplikasi dipotong menjadi bagian-bagian dan cara bagian itu saling bicara. Silent Terror memakai beberapa pola yang umum dipakai aplikasi web. Setiap kartu berisi artinya, lalu alasannya tepat di bawahnya.

🔁Client–server

Browser (client) hanya menampilkan dan mengirim permintaan; server memegang aturan dan data.

Kenapa dipilih: Game ini berisi rahasia (role). Kalau aturan ada di browser, pemain bisa mengintip atau curang lewat DevTools.

🧩Single Page Application (Angular)

Seluruh tampilan dimuat sekali; pindah halaman tidak memuat ulang situs, hanya mengganti isi layar.

Kenapa dipilih: Pergantian layar (lobby → persiapan → meja) terasa instan, dan file statisnya cukup dihosting di Vercel.

📨REST API (HTTP + JSON)

Setiap permintaan punya alamat dan metode (GET membaca, POST/PUT/DELETE mengubah). Jawabannya teks JSON.

Kenapa dipilih: Mudah diuji, mudah diamankan per alamat (siapa boleh apa), dan dipahami semua bahasa pemrograman.

⚡WebSocket (Socket.IO) untuk chat

Sambungan yang tetap terbuka sehingga server bisa mendorong chat baru ke semua pemain seketika.

Kenapa dipilih: Chat harus terasa langsung. Status permainan lain cukup dengan polling HTTP tiap detik yang lebih sederhana dan tahan putus.

🔒Server-authoritative + snapshot privat

Engine Match di backend memvalidasi setiap aksi dan membuat snapshot berbeda untuk setiap pemain.

Kenapa dipilih: Mencegah kebocoran informasi tersembunyi dan aksi ganda; frontend tidak perlu dipercaya.

🧱Backend berlapis

controllers (pintu HTTP) dan sockets (pintu chat) → services (aturan dan transaksi) → models (SQL). Controller tidak menulis SQL atau aturan game, dan model tidak commit.

Kenapa dipilih: Setiap lapisan punya satu tugas, jadi letak kode mudah ditebak dan bisa diubah tanpa merusak lapisan lain.

🧠State pertandingan di memori, arsip di MySQL

Room dan pertandingan yang sedang berjalan disimpan di memori satu proses; chat, jejak, akun, dan survei disimpan ke database.

Kenapa dipilih: Permainan cepat (tanpa query di setiap tick). Konsekuensinya: restart backend menghapus pertandingan yang sedang berjalan, jadi server dijalankan dengan satu worker.

🤖Bot sebagai pemain tanpa browser

Kode di bot/ hanya berpikir: membaca chat (IndoBERT), memutuskan (Fuzzy Mamdani), dan menulis kalimat. Vote, aksi, dan chatnya dijalankan lewat services/ yang sama dengan pemain manusia.

Kenapa dipilih: Aturan permainan hanya ada di satu tempat, jadi bot tidak bisa melakukan yang tidak boleh dilakukan manusia, dan otak bot bisa diuji tanpa server.

Ringkasan bagian 4

  • Client–server dan server-authoritative: rahasia dan aturan hanya ada di backend.
  • Angular SPA di Vercel; REST API untuk perintah dan polling, Socket.IO untuk chat seketika.
  • Backend berlapis: controllers/sockets → services → models, dengan engine game dan bot terpisah.
  • Pertandingan di memori satu proses (satu worker); arsip permanen di MySQL.
  • Bot adalah pemain tanpa browser yang lewat service yang sama dengan manusia.

5Cara kerja API (untuk yang belum pernah membuatnya)

📮
API seperti loket. Browser menulis formulir (request), menyebut loketnya (alamat), menunjukkan gelang tiket (token login), lalu menyerahkannya. Server membalas dengan nomor status (berhasil atau ditolak) dan isi jawaban dalam format JSON.

Arahkan kursor, ketuk, atau fokus (Tab) kotak bertanda i untuk melihat dari mana kotak itu, artinya, dan gunanya.

Gelang tiket: token login

  1. Saat login berhasil, server membuat token acak 32 byte. Yang disimpan di database hanya hash SHA-256-nya, jadi pencuri database tidak bisa memakai tokennya.
  2. Browser menyimpan token di localStorage dan mengirimnya di setiap request: Authorization: Bearer <token>.
  3. Setiap endpoint pemain memeriksa token lewat require_authenticated_user; endpoint admin memakai sesi panel terpisah (require_panel, berlaku 8 jam).
  4. Logout mencabut token di server. Token yang kedaluwarsa (bawaan 24 jam) ditolak dengan 401.

Dua cara browser mendapat kabar baru

🔄Polling HTTP

Halaman bertanya berkala: lobby tiap 3 detik (GET /api/rooms/{code}), meja permainan tiap 1 detik (GET /api/rooms/{code}/game), dan aplikasi tiap 3 detik mencari pertandingan aktif.

Kenapa dipilih: Tahan koneksi putus dan selalu memperbaiki dirinya sendiri: jawaban berikutnya pasti snapshot terbaru.

📣Push Socket.IO

Saat ada chat baru, server langsung mengirim event receive_chat ke semua browser di room.

Kenapa dipilih: Chat tampil tanpa menunggu polling berikutnya.

Ringkasan bagian 5

  • Request = metode + alamat + token + isi JSON; jawaban = nomor status + isi JSON.
  • Token login acak 32 byte; database hanya menyimpan hash SHA-256-nya.
  • Endpoint pemain dijaga require_authenticated_user, endpoint admin dijaga sesi panel 8 jam.
  • Polling HTTP (1–3 detik) menjaga snapshot; Socket.IO mendorong chat seketika.
  • Token fase membuat klik lama ditolak 400 setelah fase berganti.

6Frontend: dari umum ke khusus

Frontend dipecah menjadi kerangka, halaman, komponen bersama, dan service; lalu setiap fitur ditelusuri sampai keluarannya.

Umum: apa yang terjadi saat situs dibuka

  1. Browser mengunduh file statis (HTML, JavaScript, CSS, gambar) dari Vercel.
  2. Layar loading langsung tampil (meja kayu, papan judul, barisan karakter) sambil font dan gambar utama diunduh.
  3. Sekali per tab muncul ajakan layar penuh. Browser hanya mengizinkan layar penuh dari klik pemain, jadi ini ajakan, bukan paksaan.
  4. Router memilih halaman sesuai alamat, setelah guard memeriksa sesi login dan pertandingan aktif.
  5. Halaman meminta data ke backend lewat service, lalu menampilkannya. Aturan permainan tidak pernah dihitung di sini: browser hanya menggambar "foto" (snapshot) yang dikirim server dan mengirim pilihan pemain.

Layar loading

Yang terlihat sejak detik pertama sampai halaman pertama siap.

Pemain melakukan
Membuka situs, membuka tab baru, atau memuat ulang halaman.
Halaman menangani
Markup #boot-loader di index.html (meja kayu, papan judul “Silent ◆ Terror”, barisan karakter dengan kaca pembesar) tampil di paint pertama, sebelum Angular berjalan. App.ngOnInit() lalu memanggil BootLoader.start().
Service frontend
BootLoader menunggu navigasi pertama selesai (termasuk redirect guard), lalu AssetPreloader.preload(): bila halaman pertama /main, gambar kerangka Main (4 gambar: latar, binder, dua tombol), selain itu latar kayu; ditambah font Fraunces dan Patrick Hand. Skin dan kartu tidak ditunggu (diunduh Main setelah tampil).
Hasil di layar
Setelah siap (paling lama 4.000 ms) dan sapuan kaca pembesar selesai (2.400 ms), layar memudar lalu dihapus. Jaringan lambat atau offline tetap masuk ke aplikasi setelah batas waktu.
Disimpan di browser
Tidak ada.

Undangan dan tombol layar penuh

Halaman menangani

Login (username atau email + password)

Menukar username/password dengan token sesi.

Pemain melakukan
Mengisi username (atau email) dan password, lalu Log In. Tombol mata menampilkan password.
Halaman menangani
Auth.kirimLogin(): username dirapikan, keduanya wajib diisi (“USERNAME WAJIB DIISI.”, …), form dikunci selama request (isSubmitting) dan selalu dibuka lagi.
Dikirim ke backend
POST /api/auth/login {username, password}, batas 15 detik.
Backend mengerjakan
limit_auth() (15 percobaan/menit), lalu AuthService.login(): cari akun (email bila ada @), akun harus aktif, verify_password() PBKDF2-SHA256; token acak 32 byte.
Database
Dibaca user_accounts (+ account_identities untuk email); ditulis auth_sessions: hanya hash SHA-256 token dan masa berlakunya.
Hasil di layar
completeLogin() lalu pindah ke /main. Gagal: describeLoginError() → “USERNAME ATAU PASSWORD SALAH.” (401), “TERLALU BANYAK PERCOBAAN…” (429), “TIDAK BISA TERHUBUNG KE SERVER…” (0), dsb.
Disimpan di browser
shadow_heist_access_token, shadow_heist_access_token_expires_at, shadow_heist_user = {username, displayName, skinId} di localStorage; shadow_heist_game_entry dihapus. Browser menolak storage → pesan khusus.

Daftar akun (Register)

Akun baru langsung login.

Pemain melakukan
Mengisi username, nama lengkap (nama tampilan), password, dan ulangi password.
Halaman menangani
Auth.register(): username ^[A-Za-z0-9_]{3,40}$, nama 1–100 karakter tanpa karakter kontrol, password 10–128 dan sama dengan konfirmasinya.
Dikirim ke backend
POST /api/auth/register {username, display_name, password, password_confirmation}.
Backend mengerjakan
Validasi ulang (RegisterRequest), register_account(): nama bot, admin, dan user1 dicadangkan; password di-hash (salt acak); akun + email opsional + sesi dalam satu transaksi.
Database
Ditulis user_accounts, account_identities (bila ada email), auth_sessions.
Hasil di layar
201 → sama seperti login, langsung ke /main. 409 → “Username sudah digunakan. Pilih username lain atau login.”
Disimpan di browser
Sama seperti login; kolom password dikosongkan.

Login Google

Tombol resmi Google, diverifikasi di backend.

Pemain melakukan
Halaman login selesai dimuat (tombol disiapkan otomatis); pemain mengklik ikon Google dan memilih akun.
Halaman menangani
siapkanTombolGoogle() hanya di HTTPS/localhost; lalu loadGoogleIdentity() memuat SDK resmi (batas 12 detik) dan menggambar tombol ikon bulat. Callback Google → tukarKredensialGoogle().
Dikirim ke backend
GET /api/auth/google/config → client_id; POST /api/auth/google/challenge → nonce sekali pakai; POST /api/auth/google {credential, nonce}, batas 20 detik.
Backend mengerjakan
Origin harus diizinkan (403); verify_google() memeriksa token dan nonce; google_account(): akun lama lewat google_subject, akun baru username google_<acak> dengan nama dari Google. Email yang sama dengan akun lain tidak digabung.
Database
account_identities, user_accounts, auth_sessions.
Hasil di layar
Berhasil → /main. 409 → “Email sudah terdaftar. Gunakan metode login awal.”; gagal lain → pesan Google dan tombol disiapkan ulang.
Disimpan di browser
Sama seperti login. Token Google tidak disimpan.

Hasil di layar
Snapshot terbaru; baki aksi hanya berisi tombol, tanpa teks status. Penanda privat di kartu: Target, ◆ Incaran (pilihan rekan), hasil Intip, Jaga, GAG, Disandera dicap GAGAL (Hitman); cap Disandera korban publik untuk semua. Ditolak → alasan dari engine (lihat tabel pesan penolakan di bagian 7).

7Backend: dari umum ke khusus

Backend dipecah per pintu (HTTP, socket, jam), per service, dan per aturan permainan, masing-masing dari masukan sampai keluarannya.

Umum: satu program, dua pintu

Backend adalah satu program Python yang menjalankan FastAPI (REST API) dan Socket.IO (chat) di port yang sama, dengan satu worker karena room dan pertandingan disimpan di memori proses itu. Semua kodenya ada di backend/app/; path file backend di bagian ini ditulis relatif terhadap folder itu (mis. game/match_engine.py).

  • Saat diimpor: main.py tidak merangkai bagian-bagian. sio dibuat di sockets/server.py, event-nya didaftarkan sockets/chat.py, dan pengatur bot dibuat di bot/bot_controller.py, semuanya saat file itu diimpor. main.py cukup mengimpor, memasang sio ke aplikasi, lalu menyalakan jam.
  • Saat menyala (lifespan()): koneksi MySQL dicek, konfigurasi AI dan konfigurasi otak NPC dari panel dimuat, otak bot (IndoBERT + Fuzzy) mulai dimuat di latar agar server langsung melayani, lalu jam permainan dinyalakan.
  • Jam permainan: tugas asyncio yang berulang selamanya: room_service.perbarui_fase_semua_room(), npc_service.jalankan_bot_yang_sudah_waktunya(), tidur 0,5 detik. Error satu putaran dicatat dan tidak mematikan jam.
  • Satu port, dua protokol: objek yang dijalankan uvicorn adalah socketio.ASGIApp(sio, other_asgi_app=app): request Socket.IO ditangani sio, sisanya diteruskan ke FastAPI.
  • Saat berhenti: jam dibatalkan, task bot dihentikan, thread otak ditutup, pool database dilepas.

Arahkan kursor, ketuk, atau fokus (Tab) kotak bertanda i untuk melihat dari mana kotak itu, artinya, dan gunanya.

8Bot AI: telinga, otak, dan mulut

Rangkuman otak bot untuk pembaca sistem; isi rinci tiap tahap ada di dokumen AI lain.

Bot di Silent Terror adalah pemain tanpa layar. Ia melihat permainan lewat snapshot miliknya sendiri, sama seperti pemain manusia, lalu bertindak lewat service yang sama. Otaknya terdiri dari tiga bagian: telinga (NLU: dua model IndoBERT membaca chat), otak (Fuzzy Mamdani dua tahap: [FUZZY 1] menilai setiap pemain, [FUZZY 2] memilih tindakan), dan mulut (NLG: rencana chat ditulis menjadi kalimat oleh LLM atau templat). Semua kodenya ada di backend/app/bot/.

Pipa satu langkah bot

Arahkan kursor, ketuk, atau fokus (Tab) kotak bertanda i untuk melihat dari mana kotak itu, artinya, dan gunanya.

  1. Jadwal: jam 0,5 detik memanggil jalankan_bot_yang_sudah_waktunya. Bot hidup yang tidak sibuk melangkah kira-kira tiap 3 detik (bawaan NPC_STEP_SECONDS); bot yang baru dipanggil atau dituduh chat boleh melangkah lebih cepat (paling cepat 1 detik).
  2. Lihat: RoomService.lihat_untuk_bot memberi snapshot milik bot dan token fase.
  3. Dengar dan pikir (thread keputusan, batas 25 detik): ingatan mencatat snapshot, IndoBERT membaca chat baru, lalu putuskan() memilih vote, aksi malam, dan rencana chat.
  4. Bertindak: vote atau aksi rahasia langsung dikirim ke engine lewat RoomService.pilihan_bot. Bila fase berganti selama bot berpikir, keputusan dibuang.
  5. Bicara: bot meminta giliran bicara (paling banyak 3 bot menyusun kalimat bersamaan di satu pertandingan), penulis kalimat bekerja (batas 25 detik, lalu templat dalam 10 detik), jeda mengetik 1–4 detik, lalu chat disimpan dan disiarkan.
  6. Catat: jejak langkah disimpan untuk menu Checker, dan IndoBERT membaca kalimat bot supaya bot lain bisa menanggapinya.

bot/ingatan.py

bot/fuzzy_controller.py

bot/nlg.py

Mulut. Rencana chat menjadi kalimat: rantai penulis LLM, pemeriksa aturan, lalu templat sebagai cadangan.

bot/penjelasan.py

bot/simulasi.py

Event Socket.IO

connect

browser → server. Jalan saat browser menyambung: mengecek siapa yang masuk dan ke room mana, sebelum sambungan boleh menerima chat. auth = data dari browser (token, room_code). environ tidak dipakai, tapi wajib ada karena Socket.IO mengirimnya.

disconnect

browser → server. Jalan saat browser terputus: hanya menghapus catatan sambungan. Keanggotaan room tetap, jadi pemain yang memuat ulang halaman bisa kembali ke room yang sama.

send_chat

browser → server. Jalan saat pemain mengirim chat. Semua tahapnya ada di chat_service; di sini hanya penolakannya yang dikirim balik.

receive_chat

server → browser, dikirim dari bot_controller.py, chat_service.py. Didengar frontend.

system_alert

server → browser, dikirim dari chat.py. Didengar frontend.

File SQL yang mengubah struktur database secara berurutan.

Transaksi

Sekelompok penulisan database yang berhasil semua atau dibatalkan semua.

Kunci agar dua permintaan bersamaan tidak mengubah data yang sama berbarengan.

Logika bertingkat (rendah/sedang/tinggi) yang mengubah bukti 0–1 menjadi nilai keputusan.

Pembuatan kalimat: rencana chat bot ditulis LLM atau templat.

LLM

Model bahasa besar yang menulis kalimat bot (OpenRouter atau Ollama).

Persona

Catatan satu langkah bot atau satu chat untuk menu Checker.

Docker / container

Paket program beserta kebutuhannya yang dijalankan terisolasi di server.

Reverse proxy (Caddy)

Penjaga pintu yang menerima HTTPS lalu meneruskan ke backend.

CORS

Aturan browser tentang situs mana yang boleh memanggil API.

CSP / sandbox

Header keamanan; dokumen dibuka di origin terpisah sehingga tidak bisa membaca data panel.

JSON

Format teks untuk data terstruktur (kunci dan nilai) yang dikirim antara browser dan server.

HTTPS

HTTP yang dienkripsi, sehingga isi permintaan tidak bisa dibaca di jalan.

Hash (SHA-256, PBKDF2)

Sidik satu arah dari sebuah teks. Server menyimpan hash token dan password, bukan teks aslinya; PBKDF2 sengaja lambat supaya password sulit ditebak.

Cara enkripsi dua arah untuk API key dan token tunnel di database panel; kuncinya ada di .env.

localStorage / sessionStorage

Penyimpanan kecil di browser; localStorage bertahan setelah tab ditutup, sessionStorage hilang bersama tab.

CDN

Jaringan server penyebar file statis yang dekat dengan pengguna (di sini Vercel).

VM

Komputer virtual yang disewa di cloud (Azure) tempat backend dan database berjalan.

Thread / worker

Jalur kerja paralel di dalam satu program; backend memakai satu worker dan beberapa thread untuk IndoBERT dan LLM.

Tunnel

Saluran yang membuka layanan di laptop (ai-docker) ke internet tanpa membuka port router.

Commit

Satu titik simpan perubahan kode di git, dikenali dari kode pendek seperti 46f0586.

Kesimpulan akhir

Silent Terror adalah aplikasi client–server yang sengaja menaruh semua keputusan di server. Browser (Angular di Vercel) hanya menampilkan snapshot privat dan mengirim pilihan pemain; backend Python di VM Azure memegang aturan, data, dan bot.

  • Backend berlapis: controllers dan sockets sebagai pintu, services sebagai aturan dan penentu transaksi, models sebagai SQL, engine Match sebagai aturan permainan, dan bot sebagai pemain tanpa browser. 61 endpoint dan 3 event socket masuk melayani pemain dan admin.
  • Satu aturan untuk semua: manusia dan bot lewat RoomService di bawah lock yang sama, jadi bot tidak bisa curang dan aturan hanya ditulis sekali (14 skenario aturan diuji saat dokumen dibangun).
  • Bot AI: IndoBERT membaca chat, Fuzzy Mamdani (21 sistem) memutuskan, dan LLM atau templat menulis kalimat; setiap langkah tercatat untuk panel Checker.
  • Data: pertandingan berjalan di memori (cepat, satu worker), arsip permanen di MySQL (15 tabel) lewat transaksi; struktur berubah hanya lewat migrasi.
  • Survei dan panel: survei sekali per pertandingan dengan opsi Lainnya dan urutan yang diatur admin; panel delapan menu dengan login terpisah dan dokumen dalam sandbox.
  • Deployment: Vercel untuk frontend, Docker Compose (Caddy, backend, MySQL) di VM Azure, dan LLM di OpenRouter atau laptop ai-docker.
